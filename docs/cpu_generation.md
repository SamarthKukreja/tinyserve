# CPU Generation Baseline

Wave 3 connects the synthetic weight fixture to a complete, single-sequence CPU path: byte-token embedding, every configured decoder block, final RMSNorm, LM-head logits, token selection, and autoregressive generation.

## Decode behavior

- Greedy decoding uses the lowest token ID when logits tie.
- A positive temperature enables seeded categorical sampling.
- `top_k=0` keeps the full vocabulary; a positive value retains the highest `k` logits.
- The default seed is zero and can be set explicitly.
- `max_new_tokens` is enforced before decoding, together with the model's maximum sequence length.
- `--decode-mode no-cache` preserves full-prefix recomputation for correctness and benchmarking.
- `--decode-mode kv-cache` incrementally processes one token and reuses each layer's stored keys and values.
- No-cache remains the default so existing commands retain their behavior.

## Fixture CLI

After a normal test-enabled build creates `build/fixtures/dummy.tserve`:

```bash
./build/tinyserve generate \
  --model build/fixtures/dummy.tserve \
  --prompt "Hello" \
  --max-tokens 4
```

Raw IDs can bypass the temporary byte tokenizer:

```bash
./build/tinyserve generate \
  --model build/fixtures/dummy.tserve \
  --tokens 65,66 \
  --max-tokens 4 \
  --temperature 0.8 \
  --top-k 8 \
  --seed 42 \
  --decode-mode kv-cache
```

The CLI reports token IDs and escaped byte output. It deliberately labels every current run `synthetic_fixture_unverified`.

## Limitations

The included model is synthetic, the byte tokenizer is not Qwen/Llama compatible, and generated bytes have no language-quality meaning. Wave 5 adds a fixture-validated contiguous cache and a local fixture benchmark, but no real checkpoint, paged cache, batching, server, or streaming path.
